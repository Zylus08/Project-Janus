## 2. Killer Heuristic Invariant Correctness Audit

A systematic code and behavioral audit of `src/janus/search.py` was conducted across all core search invariants:

### 2.1 Cutoff Gating & Beta-Cutoff Semantics
- **Condition Audit:** In `_negamax`, line 264 evaluates `alpha = max(alpha, score)` followed by `if alpha >= beta:`.
- **Pre-Loop Guard:** When entering the move loop, the transposition table check (lines 235-244) returns immediately if a cached TT score satisfies the beta-cutoff condition. Thus, at loop entry, `alpha < beta` is mathematically guaranteed.
- **Beta-Cutoff Identification:** Inside the move loop, `alpha >= beta` triggers if and only if `score >= beta` for the current move.
- **Move Filter:** The killer recording condition strictly checks:
  ```python
  if not board.is_capture(move) and move.promotion is None:
  ```
  Because `board.pop()` is executed in the `finally` block before this check, the board is restored to the position prior to move execution. `board.is_capture(move)` accurately evaluates whether `move` is a capture in that state (including en-passant captures). Promotions (`move.promotion is None`) are excluded.

### 2.2 Table Lifecycle & State Isolation
- **Search Boundary Reset:** `self.killers` is re-initialized at the root of `search()` (line 305):
  ```python
  self.killers = [[None, None] for _ in range(self.max_killers_ply)]
  ```
- **Iterative Deepening Retention:** Because line 305 precedes the `for depth in range(1, max_depth + 1):` loop, killers discovered during shallower depths persist into deeper iterations of the same root search, accelerating move ordering.
- **Cross-Search Isolation:** Each call to `search()` clears the table; killer states do not leak between moves or games.
- **Ply Indexing & Depth Safety:** Maximum supported depth is bounded by `self.max_killers_ply = 64`. Every lookup and store checks `ply < len(self.killers)`. Searches exceeding 64 plies safely degrade to unboosted quiet move ordering without raising `IndexError`.

### 2.3 Duplicate Suppression & Slot Shifting
- **Two-Slot Shift Logic:**
  ```python
  if ply < len(self.killers) and self.killers[ply][0] != move:
      self.killers[ply][1] = self.killers[ply][0]
      self.killers[ply][0] = move
  ```
  If `move` is already in Slot 0, no shift occurs. If `move` was in Slot 1 and causes a cutoff, Slot 0 and Slot 1 swap places. Duplicate entries across both slots are prevented.

### 2.4 Legality & Immunity to Stale Entries
- **Candidate Pool:** In `_ordered_moves`, the list being sorted is initialized strictly as `moves = list(board.legal_moves)`.
- **Pure Scoring Role:** `self.killers` is never appended or merged into the move list; it serves purely as a lookup key inside `_move_order_score`. Stale or illegal killer moves from sibling branches cannot be played because they are absent from `board.legal_moves`.

### 2.5 Move Ordering Stratification & Losing Captures
The implemented score ranges create a strict hierarchy:
1. **TT Move:** `10,000,000`
2. **Winning / Equal Captures (MVV/LVA):** `980,000 – 1,200,000`
3. **Pawn Promotions:** `800,000 – 800,005`
4. **Killer 1:** `700,000`
5. **Killer 2:** `600,000`
6. **Quiet Moves:** `0`

> [!NOTE]
> **Implementation Clarification regarding Losing Captures:**
> Because Janus currently uses static MVV/LVA (`1,000,000 + 10 * victim - attacker`) without Static Exchange Evaluation (SEE), all legal captures (even tactically losing ones like QxP when defended) score $\ge 980,000$. Consequently, all captures are ordered ahead of promotions and killers in the current implementation.

### 3.4 Key Architectural Finding: In-Process Memory Fragmentation
During multi-run testing within a single persistent Python process, runtime on Depth 4 was observed to degrade from 5.6s to 15-16s across subsequent runs despite `engine.tt.clear()`. Investigation confirmed this is caused by CPython's generational garbage collector scanning millions of short-lived `chess.Move` objects and heap fragmentation from repeated large dictionary allocations. When run as independent processes (or under UCI protocol), garbage accumulation does not occur, and runtime remains firmly at **5.31s**.

## 4. In-Depth Subsystem Profiling (`cProfile`)

A full `cProfile` analysis was performed across the benchmark suite at Depth 4. Total profiled execution time was **33.95s** (the profiling instrumentation adds ~6x dilation over native execution due to Python function call interception).

### 4.1 Subsystem Breakdown (Cumulative & Self Time)

| Subsystem | Functions Included | Self Time | % Self | Cumulative Time | Key Hotspots |

| **Negamax Search Control** | `_negamax`, loop overhead, alpha-beta bounds | 0.28s | 0.8% | **33.94s (100%)** | 13,668 internal negamax nodes |

### 4.2 Major Bottlenecks Identified

1. **Redundant Stalemate Checking:**
   `_terminal_score` is called at the entrance of every node in `_negamax` and `_quiescence` (71,196 times). It unconditionally runs:
   ```python
   board.is_stalemate() or board.is_insufficient_material() or board.is_fivefold_repetition() or board.is_seventyfive_moves()
   ```
   In `python-chess`, `is_stalemate()` executes a full legal move generator (`generate_legal_moves()`) just to check if `len(moves) == 0`. This redundant move generation consumes **5.13s of execution time**. In quiescent search and internal negamax nodes, generating legal moves just for stalemate before the search even begins is purely wasted work.

2. **Transposition Table String Serialization:**
   `_key(board)` currently invokes `board.fen(en_passant="legal")`. Building, formatting, and hashing 60-character FEN strings for hash lookups consumes **1.74s for only 3,786 calls (~0.46ms per call)**. At deeper searches where TT calls reach 100,000+, FEN formatting would dominate search runtime.

3. **Bitboard Scanning in Static Evaluation:**
   `evaluate_white` calls `chess.scan_forward(mask)` nearly 2 million times (`1,995,070` calls), consuming 2.07s of pure Python iteration overhead.

## 5. Candidate Ranking for Milestone v0.11

Based on profiling evidence, implementation complexity, correctness risk, and potential playing strength impact, the top three candidates are:

### Rank 1: Terminal Checking & Stalemate Redundancy Elimination
- **Description:** Remove redundant `is_stalemate()` and `is_checkmate()` calls from `_terminal_score`. In `_negamax`, detect checkmate and stalemate directly from `moves`: if `not moves`, return checkmate score if `in_check` else draw (`0`). In `_quiescence`, skip repetition and fifty-move checks unless required, and avoid legal move generation on non-check positions.
- **Estimated Benefit:** **15% to 25% search speedup** across all depths without changing a single node count or search decision.
- **Correctness Risk:** **Very Low.** Chess rules are strictly preserved by checking `in_check` when `len(moves) == 0`.
- **Implementation Complexity:** **Low** (~15 lines of code in `src/janus/search.py`).

### Rank 2: Zobrist Hashing for Transposition Table
- **Description:** Replace `board.fen(en_passant="legal")` with integer Zobrist hashing (`chess.polyglot.zobrist_hash(board)` or incremental XOR bitboard hashing).
- **Estimated Benefit:** Eliminates all string allocations and ASCII formatting in TT lookups, speeding up each TT probe by **>10x**. Crucial for scaling beyond Depth 4.
- **Correctness Risk:** **Very Low.** Python-chess has heavily tested polyglot Zobrist hashing built in.
- **Implementation Complexity:** **Low-to-Medium.**

### Rank 3: Principal Variation Search (PVS) with Zero-Window Pruning
- **Description:** With the killer heuristic achieving a **77.4% first-move cutoff rate**, the first move searched is overwhelmingly the best move. PVS searches subsequent sibling moves with a null/zero window `[-alpha-1, -alpha]` to quickly prove they fail low, only re-searching with a full window if they beat alpha.
- **Estimated Benefit:** **15% to 30% node count reduction** at depth $\ge 5$.
- **Correctness Risk:** **Low-to-Medium.** Re-search logic on fail-high must maintain exact alpha-beta bounds.
- **Implementation Complexity:** **Medium.**
