## 1. Executive Summary

Milestone **v0.12** replaces the expensive FEN-string transposition table (TT) key generation in Project Janus (`src/janus/search.py`) with a compact, 64-bit integer Polyglot Zobrist hash (`chess.polyglot.zobrist_hash(board)`).

### Key Results
- **Key Generation Speedup:** Time spent computing TT keys dropped from **1.095s to 0.296s (3.70x speedup)** across benchmark search profiling, reducing per-call key generation from ~286 µs down to 77 µs.
- **Transposition Discovery & Node Reduction:** Because the legacy FEN key erroneously distinguished quiet move orders via halfmove clock and fullmove number, it prevented valid transposition hits. The sound Zobrist key recovers these transpositions, reducing Depth 4 benchmark nodes from **71,195 to 68,677 (-2,518 nodes, -3.54%)**, while maintaining **100% agreement** on root evaluations, best moves, and principal variations.
- **Search Runtime Improvement:** Contemporary back-to-back testing under identical hardware conditions demonstrated a **+5.8% end-to-end speedup** at Depth 4 (median 4.828s FEN vs 4.547s Zobrist) and a **+3.8% speedup** at Depth 3 (median 0.812s FEN vs 0.781s Zobrist).
- **Draw Rule & Repetition Safety:** An explicit draw-proximity guard (`(board.halfmove_clock + depth < 150) or entry.score == 0`) ensures that TT cutoffs are never taken when a mandatory seventy-five-move draw could intervene within the search horizon. Path-dependent repetition checks continue to take precedence before TT probing.
- **Regression Suite:** Expanded from 49 to **65 passing tests** (16 new targeted tests in `tests/test_zobrist_tt.py`), with zero regressions across all search, evaluation, human robustness, and killer heuristic suites.

## 3. Existing TT Key Semantics Audit

The legacy implementation used:
```python
@staticmethod
def _key(board: chess.Board) -> str:
    return board.fen(en_passant="legal")
```

A standard FEN string contains 6 fields:
1. **Piece placement:** Identifies the exact squares occupied by all pieces.
2. **Side to move:** White (`w`) or Black (`b`).
3. **Castling rights:** Remaining castling availability (`KQkq` or subsets).
4. **En-passant target square:** When filtered with `en_passant="legal"`, included only if an enemy pawn can legally make an en-passant capture.
5. **Halfmove clock:** Count of halfmoves since the last pawn advance or capture.
6. **Fullmove number:** Turn counter incremented after Black's move.

### The TT Defect in the Legacy FEN Key
Fields 1–4 constitute the **intrinsic position identity** and govern all legal moves and static evaluations. Fields 5 and 6 (halfmove clock and fullmove number) do **not** alter legal move availability or static board evaluation:
- In the legacy FEN key, two paths transposing into the exact same chess position with different quiet move orders (e.g. 1. Nf3 d5 2. c4 vs 1. c4 d5 2. Nf3) received **different** FEN strings because their halfmove clocks or fullmove numbers differed.
- This caused false TT misses, forcing the search to re-expand identical subtrees.
- In `open_game`, this bug accounted for 2,518 redundant node expansions at Depth 4.

## 4. Zobrist Key Design & Correctness Rationale

### 4.1 Key Contract
The new key helper is defined as:
```python
@staticmethod
def _key(board: chess.Board) -> int:
    """Return a 64-bit integer Polyglot Zobrist hash of the current position."""
    return chess.polyglot.zobrist_hash(board)
```

The transposition table dictionary is typed:
```python
self.tt: dict[int, TTEntry] = {}
```

### 4.2 Semantic Equivalence Verification
1. **Piece placement & Turn:** Fully encoded in the Polyglot 64-bit random piece-square and turn keys.
2. **Castling rights:** Distinct random keys for white/black kingside and queenside castling rights.
3. **En-passant semantics:** In `python-chess`, `chess.polyglot.zobrist_hash` adheres to the Polyglot standard: the en-passant file is hashed **only** if an opposing pawn is positioned to legally capture en-passant. This identically matches `board.fen(en_passant="legal")`.
4. **Collision Policy:** With 64-bit keys, the collision probability for $N$ keys is $p \approx N^2 / 2^{65}$. For $N = 7 \times 10^4$ nodes, $p \approx 1.3 \times 10^{-10}$. For $N = 10^6$ (the TT maximum capacity), $p \approx 2.7 \times 10^{-8}$. Standard single 64-bit integer keys are universally standard in top chess engines (Stockfish, Crafty) and introduce no material risk.
5. **Memory and Dict Lookup Efficiency:** An integer key is stored compactly and Python hashes 64-bit integers in $O(1)$ without string allocation, string hashing, or character-by-character string comparisons.

## 5. Draw-Rule and Repetition Considerations

### 5.1 Seventy-Five-Move Draw Proximity Guard
While minimax scores are position-independent for low halfmove clocks, proximity to the mandatory seventy-five-move draw threshold (`halfmove_clock >= 150`) introduces path dependence:
- A non-zero score stored at `halfmove_clock = 0` could claim a win, but if probed at `halfmove_clock = 148` with search depth 3, the game would force a draw at ply 2 (`is_seventyfive_moves() == True`, score 0).
- To prevent unsafe cache hits near the threshold, a guard was added to `_negamax`:
```python
# Near the seventy-five-move draw threshold, non-zero cached scores
# cannot guarantee that a forced draw won't intervene within the search horizon.
if ply > 0 and entry.depth >= depth:
    if (board.halfmove_clock + depth < 150) or entry.score == 0:
        if entry.flag == "exact":
            return tt_score, ([] if tt_move is None else [tt_move])
        if entry.flag == "lower":
            alpha = max(alpha, tt_score)
        elif entry.flag == "upper":
            beta = min(beta, tt_score)
        if alpha >= beta:
            return tt_score, ([] if tt_move is None else [tt_move])
```
- If `board.halfmove_clock + depth < 150`: No line in the current search subtree can reach the 75-move threshold, making score cutoffs provably safe.
- If `entry.score == 0`: A draw score remains sound even if a 75-move draw occurs.
- If `board.halfmove_clock + depth >= 150 and entry.score != 0`: Score cutoff is suppressed; the node is searched explicitly while preserving `entry.best_move` for move ordering.

### 5.2 Repetition Behavior
- Mandatory draws (`is_fivefold_repetition()`, `is_seventyfive_moves()`, `is_insufficient_material()`) are checked at the start of `_negamax` **before** the TT probe. If the current game path reaches fivefold repetition, `0, []` is returned immediately, preventing TT cutoffs from masking repetitions.
- *Engine limitation note:* Project Janus currently does not implement 3-fold repetition detection in search (consistent across v0.10, v0.11, and v0.12). Zobrist hashing neither introduces nor resolves 3-fold repetition handling; this is documented for future milestones.

## 9. Limitations & Unresolved Risks

1. **Threefold Repetition Detection:** Search detects fivefold repetition and seventy-five moves, but not voluntary threefold repetition claims. This is a pre-existing engine limitation not addressed in this milestone.
2. **TT Size and Eviction Policy:** Janus uses an entry-count cap (`self.tt_max_entries = 1_000_000`) with a full table clear (`self.tt.clear()`) upon reaching capacity. While sufficient for fixed-depth benchmarks, depth-based or age-based replacement policies would improve memory retention under deep searches.
3. **Single 64-bit Key:** While 64-bit Zobrist keys have a negligible collision probability ($< 10^{-9}$), pairing with an independent 32-bit signature or full move verification could offer mathematical guarantees if TT capacity is increased to tens of millions of entries in the future.

## 10. Recommendation for v0.13

With terminal detection (v0.11) and transposition table Zobrist hashing (v0.12) complete:
1. **Move Ordering / History Heuristic:** The killer heuristic orders quiet refutations, but a History Heuristic (indexing quiet moves that cause beta cutoffs across all positions) would substantially improve quiet move ordering in complex positions like `open_game`.
2. **Principal Variation Search (PVS) / Aspiration Windows:** Now that transposition table lookups and bounds are fast and verified sound, implementing aspiration windows or PVS will yield substantial tree reductions at Depth 5+.
