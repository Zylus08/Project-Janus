## 1. Executive Summary

Milestone **v0.14** performs an empirical audit of the quiet-move history heuristic introduced in v0.13, eliminates Python move-ordering interpreter overhead in `_ordered_moves`, and evaluates the engine's architectural readiness for **Principal Variation Search (PVS)**.

### Key Results
- **Robustness Confirmed via 10 Interleaved Repetitions:** Testing 10 interleaved independent-process pairs at Depth 4 conclusively demonstrated that the history heuristic provides a robust **+6.32% runtime speedup** (median 4.454s baseline disabled vs 4.172s enabled) alongside lower runtime variance (IQR 0.531s vs 0.828s) and a **-2.40% search tree reduction** (-1,648 nodes).
- **Profiling & Overhead Diagnosis:** `_move_order_score` was called **157,317 times** during the benchmark suite. In the original implementation, each call performed repeated attribute and length checks (`self.killers[ply]`, `self.history`, `self.enable_history`).
- **Targeted Move-Ordering Optimization:** Pre-fetching `k1`, `k2`, and `history` once per node in `_ordered_moves` and short-circuiting trivial move lists (`len(moves) <= 1`) eliminated repeated indirection overhead, boosting Depth 4 median runtime to **3.711s (+16.68% speedup over baseline disabled)** with an exceptionally tight IQR of **0.173s**.
- **Minimax Tree Invariance:** Total nodes (13,756 at Depth 3, 67,029 at Depth 4), best moves, root evaluations, and principal variations remained **100% identical** before and after the optimization.
- **Regression Suite:** Expanded from 74 to **76 passing tests** (2 new tests in `tests/test_history_heuristic.py`).
- **PVS Readiness:** With a confirmed **78.88% first-move cutoff rate** and fast move ordering, Janus satisfies all architectural prerequisites for PVS.

## 4. Profiling History Overhead

A cProfile investigation (`analysis/v0.14/history_profiling.json`) revealed the function-level profile of move ordering:

1. **`_update_history` Cost:** Called 1,625 times during Depth 4 search, with cumulative execution time **< 0.001s**. Table updates contribute negligible overhead.
2. **`_move_order_score` Overhead:** Called **157,317 times** across search (`96,856` in `_ordered_moves`, `60,461` in `_quiescence`), consuming **1.011s cumulative time**.
3. **Repeated Indirections:** In `_ordered_moves`, the inner `lambda move: self._move_order_score(...)` repeatedly:
   - Evaluated `ply < len(self.killers)`.
   - Indexed `self.killers[ply][0]` and `self.killers[ply][1]`.
   - Evaluated `self.enable_history` and `self.history`.
   - Evaluated multiple `if` branches even after identifying captures.

## 5. Implementation Improvement: Optimized `_ordered_moves`

### 5.1 The Change
`_ordered_moves` in `src/janus/search.py` was refactored to pre-fetch node-constant state once per node and use an early-exit scoring cascade:

```python
def _ordered_moves(
    self,
    board: chess.Board,
    tt_move: Optional[chess.Move] = None,
    ply: int = 0,
) -> list[chess.Move]:
    moves = list(board.legal_moves)
    if len(moves) <= 1:
        return moves

    k1 = self.killers[ply][0] if ply < len(self.killers) else None
    k2 = self.killers[ply][1] if ply < len(self.killers) else None
    history = self.history if self.enable_history else None

    def score_move(move: chess.Move) -> int:
        if tt_move is not None and move == tt_move:
            return 10_000_000

        if board.is_capture(move):
            victim = board.piece_at(move.to_square)
            victim_value = 100 if board.is_en_passant(move) else (
                0 if victim is None else MVV_LVA_PIECE_VALUES[victim.piece_type]
            )
            attacker = board.piece_at(move.from_square)
            attacker_value = (
                0 if attacker is None else MVV_LVA_PIECE_VALUES[attacker.piece_type]
            )
            score = 1_000_000 + 10 * victim_value - attacker_value
            if move.promotion:
                score += 800_000 + move.promotion
            return score

        if move.promotion:
            return 800_000 + move.promotion

        if move == k1:
            return 700_000
        if move == k2:
            return 600_000

        if history is not None:
            return history[move.from_square][move.to_square]

        return 0

    moves.sort(key=score_move, reverse=True)
    return moves
```

### 5.2 Correctness and Invariance
- If `len(moves) <= 1`: Short-circuits sorting immediately.
- Preserves exact numeric score values and ordering hierarchy (`TT > Capture > Promotion > Killer 1 > Killer 2 > History > Unscored`).
- Retains `_move_order_score` as a public method on `JanusSearch` for backward compatibility with external tests.

## 8. Principal Variation Search (PVS) Readiness Assessment

### 8.1 Theoretical Motivation
Janus currently achieves an overall **first-move cutoff rate of 78.88%** across the benchmark suite (2,151 first-move cutoffs out of 2,727 total cutoffs). This indicates that move ordering is high quality, meeting the primary precondition for PVS.

### 8.2 Architectural Blueprint for PVS

1. **Child Search Windows:**
   - **First move ($i = 0$):** Full-window search: `_negamax(board, depth - 1, -beta, -alpha, ply + 1)`.
   - **Subsequent moves ($i > 0$):** Null-window scout search: `_negamax(board, depth - 1, -alpha - 1, -alpha, ply + 1)`.
2. **Re-search Condition:**
   - If the scout search returns `score > alpha` and `score < beta` (a fail-high on a non-PV move):
   - Re-search with full window: `_negamax(board, depth - 1, -beta, -score, ply + 1)`.
3. **Bound and TT Entry Soundness:**
   - Scout searches that fail low store upper-bound entries in the TT.
   - If a re-search is triggered, the scout search's best move is already stored in the TT, accelerating the full re-search.
4. **Mate-Distance Score Handling:**
   - Null-window bounds `[-alpha - 1, -alpha]` near mate thresholds (`MATE_SCORE`) must not distort ply-adjusted mate evaluations.
5. **Shallow Depth & In-Check Gating:**
   - PVS should be gated to `depth >= 2` or `depth >= 3`.
   - When in check, all legal evasions should use full windows or standard alpha-beta to avoid frequent re-searches on tactical lines.

### 8.3 Validation Criteria for PVS Milestone
- **Minimax Score Invariance:** Every benchmark position must return identical root scores and best moves.
- **Scout Success Rate:** Re-search frequency on non-PV moves must remain below 10%.
- **Node & Runtime Targets:** Projected 15–30% node reduction at Depth 5+, with net wall-clock speedup.
