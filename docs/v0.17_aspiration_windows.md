## 1. Executive Summary

Milestone **v0.17** introduces **Aspiration Windows** at the root of iterative deepening in Project Janus. Aspiration search narrows the root alpha-beta search window around the score obtained from the previous completed search iteration:
$$[\alpha, \beta] = [\text{previous\_score} - \delta, \text{previous\_score} + \delta]$$

By restricting the root window to expected score fluctuations ($\delta = 35$ cp default), branches outside the window can be pruned earlier by interior alpha-beta cutoffs, reducing the total search tree size.

### Key Results
- **100% Minimax Score and Decision Invariance:** Across all six benchmark positions at depths 1, 2, 3, 4, and 5, aspiration search produces **strictly identical root scores, best moves, and legal principal variations** compared to full-window search (0 mismatches).
- **Search Tree Reductions:**
  - **Depth 3:** 13,460 $\to$ **13,439 nodes** (**-21 nodes**, -0.16%).
  - **Depth 4:** 48,308 $\to$ **48,229 nodes** (**-79 nodes**, -0.16%).
  - **Depth 5:** 189,620 $\to$ **189,535 nodes** (**-85 nodes**, -0.04%).
- **Wall-Clock Runtimes (5 Interleaved Paired Repetitions per Depth):**
  - **Depth 3:** Baseline median 0.598s vs Aspiration median 0.607s (+0.009s, +1.56%).
  - **Depth 4:** Baseline median 2.435s vs Aspiration median 2.453s (+0.019s, +0.77%).
  - **Depth 5:** Baseline median 6.919s vs Aspiration median 6.940s (+0.021s, +0.30%).
- **Empirical Speedup Assessment:**
  - In a single-threaded Python engine running at ~27,000 nodes/second, saving 85 nodes yields ~3.1 ms of raw execution time.
  - The runtime difference (+9ms to +21ms) is well within host measurement variance (IQR ranges between 50ms and 250ms).
  - As established by the milestone mandate, **aspiration windows do not provide a wall-clock speedup at depths 3–5 in Python**; instead, wall-clock performance is neutral, while tree size is reduced and minimax correctness is strictly preserved.
- **Robustness & Soundness:**
  - First iteration (depth 1) is always searched full-window (`[-INF, INF]`).
  - Forced mate scores (`abs(score) >= MATE_THRESHOLD`) safely bypass aspiration windows.
  - Fail-low and fail-high re-searches use exponential widening (`delta *= 2`) and fallback unconditionally to full window `[-INF, INF]` after at most 3 retries, mathematically guaranteeing termination.
  - Intermediate fail-low / fail-high scores are never published; only completed, exact-window iterations update the engine's best move and score.
- **Expanded Test Suite:** Full suite expanded from 88 to **102 passing tests** (14 new dedicated unit and regression tests in `tests/test_aspiration.py`).
- **Controlled Stockfish Match:** Completed 2 paired games at depth 3 without errors (1 draw by threefold repetition, 1 loss by checkmate), confirming UCI protocol stability.

## 2. Search-Flow Audit (Phase 1)

Prior to implementation, the search infrastructure in `src/janus/search.py` was inspected:
1. **Iterative Deepening Control Flow:**
   Iterative deepening executes sequentially from `depth = 1` to `max_depth`. Previously, each iteration invoked:
   ```python
   score, pv = self._negamax(board, depth, -INF, INF, 0)
   ```
2. **Root vs. Interior Node Semantics:**
   Aspiration windows are applied exclusively at `ply == 0` (the root). Interior node negamax contracts and PVS scout search logic remain completely untouched.
3. **Transposition Table Bound Semantics:**
   At root and interior nodes, TT entries compare `best_score` against the original search window `alpha_original` and `beta_original` to set `"exact"`, `"lower"`, or `"upper"` flags. Narrower root bounds produce valid upper or lower bounds in TT entries. When a re-search occurs, cached TT entries accelerate the re-search.
4. **Mate Distance Normalization:**
   Mate scores are normalized using `score +/- ply`. Because mate scores shift by search depth or defense extensions, narrowing the window around mate scores can cause pathological retries. Therefore, mate scores are explicitly gated to bypass aspiration search.

## 3. Implementation Details (Phase 2)

### 3.1 Initial Window and Activation Gating
Aspiration search is enabled via `enable_aspiration: bool = True` (configurable) with default window parameter `aspiration_delta: int = 35`.
For each depth $d \in [1, \text{max\_depth}]$:
- **Depth 1:** Full-window `[-INF, INF]` is searched unconditionally.
- **Mate Score Gating:** If `abs(best_score) >= MATE_THRESHOLD` (99,000), full-window `[-INF, INF]` is searched unconditionally.
- **Subsequent Depths ($d \ge 2$):** Aspiration search is activated with initial bounds:
  $$\alpha = \max(-\text{INF}, \text{best\_score} - \delta), \quad \beta = \min(\text{INF}, \text{best\_score} + \delta)$$

### 3.2 Safe Widening and Guaranteed Termination
If the returned root score falls outside $(\alpha, \beta)$, an aspiration re-search is triggered:
- **Fail-Low ($\text{score} \le \alpha$):** All moves scored at or below $\alpha$. The lower bound is widened:
  $$\delta \leftarrow \delta \times 2, \quad \alpha \leftarrow \max(-\text{INF}, \text{best\_score} - \delta)$$
- **Fail-High ($\text{score} \ge \beta$):** At least one move scored at or above $\beta$. The upper bound is widened:
  $$\delta \leftarrow \delta \times 2, \quad \beta \leftarrow \min(\text{INF}, \text{best\_score} + \delta)$$
- **Fallback Criterion:** If retries reach `max_aspiration_retries` (default: 3) or bounds reach mate limits ($\alpha \le -\text{MATE\_THRESHOLD}$ or $\beta \ge \text{MATE\_THRESHOLD}$), the search falls back unconditionally to:
  $$\alpha = -\text{INF}, \quad \beta = \text{INF}$$
  Because all minimax scores from `_negamax` lie strictly within $(-100,000, 100,000)$ and $\text{INF} = 1,000,000$, a search with $[-\text{INF}, \text{INF}]$ cannot fail low or fail high. This mathematically guarantees termination in at most $\text{max\_aspiration\_retries} + 1$ search calls per depth.

### 3.3 Result Publishing Invariant
Intermediate fail-low or fail-high results are never published to `best_score`, `best_pv`, or `best_move`. If a search times out or is stopped during an aspiration re-search, the iteration is aborted and the previous completed depth's score and PV are preserved intact.

## 4. Telemetry Architecture (Phase 3)

Five dedicated aspiration telemetry counters were integrated into `JanusSearch` and exported in `SearchResult`:

| Counter | Type | Reset Point | Semantics |
|---|---|---|---|
| `aspiration_iterations` | `int` | Start of `search()` | Number of root iterative-deepening iterations that initialized a narrow aspiration window ($d \ge 2$, non-mate). |
| `aspiration_fail_lows` | `int` | Start of `search()` | Number of root search attempts returning $\text{score} \le \alpha$. |
| `aspiration_fail_highs` | `int` | Start of `search()` | Number of root search attempts returning $\text{score} \ge \beta$. |
| `aspiration_researches` | `int` | Start of `search()` | Number of aspiration re-search attempts executed due to fail-low or fail-high events. |
| `aspiration_fallbacks` | `int` | Start of `search()` | Number of iterations that triggered an unconditional full-window $[-\text{INF}, \text{INF}]$ fallback. |

These counters are strictly isolated from PVS scout re-search telemetry (`researches`, `scout_searches`, `scout_fail_highs`).

6. `stalemate`: 0 nodes (terminal state, immediate return).

### 6.4 Discussion and Analysis of Findings
- **Why node savings are focused in `open_game`:**
  In positions where move ordering is already near-perfect (such as `startpos`, `white_up_rook`, and `promotion_tactic`), PVS scout searches already prune non-PV subtrees to zero-windows $[\alpha, \alpha+1]$. Aspiration windows only narrow the root bound for the first move from $[-\text{INF}, \text{INF}]$ to $[S-\delta, S+\delta]$. Unless root moves fall outside that window, interior node cutoffs for move 1 are identical. In complex positions like `open_game` where multiple root moves contend, the narrower root bound prevents branches from expanding as far, saving 85 nodes at Depth 5.
- **Why wall-clock time does not accelerate:**
  In compiled languages (C/C++, Rust), engines search millions of nodes per second, where saving thousands of nodes produces a measurable wall-clock gain. In Python, Janus searches ~27,000 nodes/sec. Saving 85 nodes represents approximately 3.1 milliseconds of computation. Setting up the aspiration window, maintaining retry state, and checking bound conditions at each iteration introduces a few microseconds of Python interpreter overhead. Consequently, runtime deltas (+9ms to +21ms) are negligible and dwarfed by normal OS thread scheduling noise (IQR 50–250ms).
