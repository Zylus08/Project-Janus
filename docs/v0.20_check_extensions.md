# Milestone v0.20 — Bounded Check Extensions Design & Validation

## 1. Executive Summary

Milestone v0.20 implements **Bounded Check Extensions** in Project Janus to allocate additional search depth to selected in-check positions. This expansion heuristic prioritizes search correctness and tactical resolution over node reduction.

### Key Results
- **Controlled Benchmark (Depths 3–5, 5 Interleaved Repetitions):**
  - **Depth 3:** Nodes increased by +10.06% (13,439 → 14,791); median runtime +8.72% (0.635s → 0.691s).
  - **Depth 4:** Nodes increased by +24.45% (26,409 → 32,867); median runtime +15.88% (1.369s → 1.586s).
  - **Depth 5:** Nodes increased by +36.95% (53,707 → 73,553); median runtime +28.77% (2.491s → 3.208s).
- **Tactical Consistency:** Root scores, best moves, and legal Principal Variations matched the baseline across all 6 benchmark positions at depths 3, 4, and 5.
- **Controlled Extension Budget:** At depth 5 across 909 eligible in-check nodes, exactly 791 extensions were applied (+1 ply each), while 118 extensions were safely suppressed by the branch budget (`max_check_extensions = 2`), preventing search explosion. Exactly 38 terminal mates were verified at extended nodes.
- **Four-Way Depth 4 Ablation:**
  - `pure_pvs`: +27.41% nodes (48,229 → 61,450; 268 extensions applied).
  - `lmr_only`: +17.75% nodes (45,239 → 53,271; 260 extensions applied).

- **Stockfish Integration Smoke Test:** 2-game paired match against Stockfish 19 completed without forfeits or illegal moves, yielding 0.5/2 (25.0%), replicating the historical smoke-test baseline.

## 2. Check Extension Policy & Architectural Design

### A. Core Extension Policy
Check extensions are applied at interior check nodes where the side to move is in check and must respond with legal evasions:
1. **Eligibility Guard:** `in_check and depth > 0`.
2. **Interior Focus:** Nominal iterative-deepening depth at root (`ply == 0`) is preserved. Extensions grant child nodes an additional ply of search.
3. **Branch Extension Budget:** Cumulative check extensions along any active search path from the root cannot exceed `max_check_extensions` (default: 2). If the budget is exhausted, `check_extensions_suppressed` is incremented and no extension is granted.
4. **Magnitude:** Conservative 1 ply (`extension = 1`).

### B. Depth Definitions & Invariants
- **Nominal Depth ($d_{\text{nominal}}$):** The target iteration depth requested by the iterative deepening controller (`for depth in range(1, max_depth + 1)`). This value remains strictly stable and is reported in `SearchResult.depth`.
- **Effective Depth ($d_{\text{effective}}$):** The search depth at the current node after applying eligible extensions:
  $$d_{\text{effective}} = d + \text{extension}$$
- **Remaining Child Depth ($d_{\text{child}}$):** The depth passed to child searches:
  $$d_{\text{child}} = d_{\text{effective}} - 1$$
- **Transposition Table Depth:** To ensure transposition table consistency, entries at extended nodes are stored with `depth = effective_depth`. Probing verifies `entry.depth >= effective_depth`, preventing shallow probes from prematurely satisfying deeper extended queries.

### C. Synergy with Selective Search Heuristics
1. **Null Move Pruning (NMP):** NMP requires `not in_check`. NMP is unconditionally bypassed at all check nodes, extended or unextended.
2. **Late Move Reductions (LMR):** LMR requires `not in_check and not gives_check`. King evasions and checking moves are strictly protected from reduction.
3. **Principal Variation Search (PVS):** Scout searches and full-window re-searches operate on `effective_depth - 1`, preserving exact PVS window semantics.
4. **Aspiration Windows:** Root aspiration retries continue to govern the full iteration window.
5. **Mate-Distance Scoring:** Extensions add search depth without corrupting distance-to-mate normalization (`-MATE_SCORE + ply`). Checkmate detection at extended nodes is recorded in `check_extensions_terminal_mates`.

## 3. Telemetry Accounting

| Telemetry Counter | Scope | Definition |
|---|---|---|
| `check_extensions_eligible` | Per node | In-check nodes with `depth > 0` |
| `check_extensions_applied` | Per node | Check nodes that received a +1 ply extension |
| `check_extension_plies` | Per node | Total plies added by check extensions |
| `check_extensions_suppressed` | Per node | In-check nodes where extension was denied by the budget |
| `check_extensions_terminal_mates` | Per node | Terminal checkmates discovered at extended nodes |

All telemetry counters cleanly reset to zero at the start of each `search()` invocation.

## 5. Stockfish 19 Integration Smoke Test

A 2-game integration smoke test was conducted against Stockfish 19 using `scripts/match.py`:
- **Opening:** Scotch Game (`e4 e5 Nf3 Nc6 d4 exd4 Nxd4`) from `benchmarks/openings.json`, seed 42.
- **Search Depth:** Fixed depth 3 per move for both engines.
- **Game 1 (Janus as White):** 1/2-1/2 draw by threefold repetition in 165 plies (12.97s).
- **Game 2 (Janus as Black):** 0-1 loss by checkmate in 45 plies (3.13s).
- **Match Score:** 0.5/2 (25.0%).
- **Verification:** All moves were verified legal by python-chess; termination reasons and PGN headers are consistent with historical baselines.
