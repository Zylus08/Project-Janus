### 1. Architectural Overview of Current Transposition Table

The Transposition Table (TT) in Project Janus is embedded directly in `src/janus/search.py` and implemented via a Python dictionary mapping 64-bit Zobrist hashes to entry dataclasses.

```
       +-------------------------------------------------------+
       |                  chess.Board                          |
       |  (pieces, turn, castling rights, en-passant square)   |
       +-------------------------------------------------------+
                                   |
                       chess.polyglot.zobrist_hash
                                   |
                                   v
                         64-bit uint key
                                   |
            +----------------------+----------------------+
            |                                             |
     Probe in _negamax                             Store in _negamax / NMP
            |                                             |
            v                                             v
    self.tt.get(key)                              self.tt[key] = TTEntry(...)
            |                                             |
     [Entry Found?]                               [Full Storage Check]
     /          \                                 len(self.tt) >= tt_max_entries
   Yes           No (miss)                                |
    |                                                   Yes -> self.tt.clear()
 [Effective Depth & Bound Check]                          |
    |                                                     v
 [Cutoff or Move Ordering]                         Unconditional overwrite
```

#### Entry Representation
The entry is defined as a Python dataclass:
```python
@dataclass
class TTEntry:
    depth: int                     # Effective search depth (depth + extensions)
    score: int                     # Mate-normalized centipawn score
    flag: str                      # Bound type: "exact", "lower", "upper"
    best_move: Optional[chess.Move] # Best move found at this node
```

Key observations on stored fields:
1. **No Age / Generation Field**: Entries lack timestamps, search generation tags, or iteration counters.
2. **No Secondary Key / Signature Verification**: Because keys are stored directly in Python's hash table, key collision resolution is handled by Python's dict; distinct positions colliding on 64-bit Polyglot hash would alias (expected probability $\approx 10^{-19}$).
3. **No Flag Bitmasking**: Flags are stored as Python strings (`"exact"`, `"lower"`, `"upper"`).

### 2. Probe Semantics & Interaction with Search

Probing occurs at the start of each `_negamax` call (lines 520–541 of `src/janus/search.py`):

1. **Root Probe Handling**:
   - `ply > 0` guard: Probes at the root (`ply == 0`) extract `tt_move` for root move ordering, but **never trigger an immediate cutoff**. This guarantees iterative deepening finishes every iteration and populates full PV lines.
2. **Depth Compatibility**:
   - Condition: `entry.depth >= effective_depth`, where `effective_depth = depth + extension`.
   - If `entry.depth < effective_depth`, the entry is insufficient for a cutoff, but `entry.best_move` is preserved and used as `tt_move` to order moves in `_ordered_moves`.
3. **Seventy-Five-Move Rule Safeguard**:
   - Condition: `(board.halfmove_clock + effective_depth < 150) or entry.score == 0`.
   - If the halfmove clock is approaching 150 (75 full moves), a non-zero winning/losing score could be truncated by an intervening mandatory draw. In this case, non-zero cutoffs are suppressed and the position is re-searched; zero scores (draws) are allowed to cutoff immediately.
4. **Bound Cutoff Logic**:
   - `"exact"`: Cutoff immediately, returning `(tt_score, [tt_move])`.
   - `"lower"`: `alpha = max(alpha, tt_score)`. If $\alpha \ge \beta$, cutoff immediately.
   - `"upper"`: `beta = min(beta, tt_score)`. If $\alpha \ge \beta$, cutoff immediately.

#### Hash-Move Ordering
In `_ordered_moves`:
```python
if tt_move is not None and move == tt_move:
    return 10_000_000
```
The hash move receives top priority ($10,000,000$), strictly ahead of good captures ($1,000,000+$), killer moves ($700,000$, $600,000$), and history moves ($0 \dots 10,000$).

### 3. Current Replacement Behavior: "Always-Replace / Clear-on-Full"

The existing replacement policy is unconditionally eager:

#### Storage Points
1. **Null Move Pruning Cutoff** (`_negamax`, line 582):
   Stores `flag="lower"`, `score=beta`, `depth=depth`, `best_move=tt_move`.
2. **Node Completion** (`_negamax`, line 720):
   Stores `depth=effective_depth`, `score=best_score`, `flag=flag`, `best_move=best_move`.

#### Replacement Logic
```python
if len(self.tt) >= self.tt_max_entries:
    self.tt.clear()
self.tt[key] = TTEntry(...)
```

#### Identified Inefficiencies & Risks in Current Design
1. **Shallow-Overwrites-Deep Anomaly ("Always Replace")**:
   When storing into an existing key (`key in self.tt`), the existing entry is unconditionally overwritten:
   - An aspiration window re-search at a shallower depth or an LMR reduced branch can overwrite a deep, exact PV entry with a shallow upper bound.
   - Example: A depth 5 search records an exact score at key $K$. Later, a reduced depth 2 branch visits $K$ and overwrites it with a depth 2 upper bound. A subsequent probe at depth 4 now misses the cutoff because $2 < 4$.
2. **Best-Move Destruction on Fail-Low**:
   When a node fails low (`best_score <= alpha_original`), `best_move` is frequently `None` (no move improved alpha). Overwriting an existing entry that already held a valid `best_move` discards the hash move, degrading move ordering in subsequent iterations.
3. **Table Flush Penalty ("Clear-on-Full")**:
   When `len(self.tt)` reaches `tt_max_entries` (default 200,000), `self.tt.clear()` flushes 100% of accumulated entries. All deep entries and root branch evaluations are discarded simultaneously, causing sudden latency spikes.
4. **Lack of Telemetry**:
   The engine currently logs 0 transposition table statistics in `SearchResult`: no counts of probes, hits, usable hits, cutoffs, stores, same-key updates, or replacements.

### 4. Mate-Score Normalization

Mate scores are dynamically normalized between root distance and ply distance:
- **`_score_to_tt(score, ply)`**:
  - If $score \ge \text{MATE\_THRESHOLD}$, return $score + ply$ (distance from root).
  - If $score \le -\text{MATE\_THRESHOLD}$, return $score - ply$ (distance from root).
- **`_score_from_tt(score, ply)`**:
  - If $score \ge \text{MATE\_THRESHOLD}$, return $score - ply$ (distance from current node).
  - If $score \le -\text{MATE\_THRESHOLD}$, return $score + ply$ (distance from current node).

This design is mathematically sound, preserves mate distance across transpositions, and is verified by `test_mate_score_normalization_in_tt`.

### 5. Proposed Replacement Policy Candidates

To eliminate shallow overwrites, preserve valuable hash moves, and improve hit rates under table capacity constraints, we formulate three distinct, independently configurable policies:

#### Candidate 1: `always_replace` (Current Baseline)
- Matches the current production policy exactly.
- Overwrites unconditionally on same-key updates.
- Calls `self.tt.clear()` when `len(self.tt) >= self.tt_max_entries`.

#### Candidate 2: `depth_preferred`
- **Same-Key Protection**:
  When storing a position whose key already exists in the TT (`old = self.tt[key]`):
  1. **Depth Guard**: Replace if `new_depth >= old.depth`.
  2. **Exact Upgrade**: Also replace if `new_flag == "exact"` and `old.flag != "exact"`.
  3. **Best Move Preservation**: If `new_best_move is None` and `old.best_move is not None`, preserve `old.best_move` in the updated entry.
  4. If `new_depth < old.depth` and not an exact upgrade, reject the replacement (retain the deeper entry).
- **Full Capacity Handling**:
  When `len(self.tt) >= self.tt_max_entries` and storing a new key:
  - Clear-on-full or shallow-eviction.

#### Candidate 3: `two_tier` (Dual-Slot / Bucketed Architecture)
- Divides capacity into two functional tiers holding at most `tt_max_entries` in total:
  - **Tier 1 (`tt_deep`)**: Protected depth-preferred storage. Entries are stored and replaced only when `new_depth >= old.depth` or upon exact upgrade.
  - **Tier 2 (`tt_recent`)**: Always-replace storage. Captures recent search nodes, shallow hits, and transient leaf bounds that fail Tier 1 qualification.
- **Probe Strategy**:
  1. Probe `tt_deep`. If hit with `depth >= effective_depth`, attempt cutoff.
  2. If miss or insufficient depth, probe `tt_recent`.
  3. Best move is harvested from whichever tier has a valid move (prioritizing `tt_deep`).
- **Store Strategy**:
  - Stored in `tt_deep` if `key in tt_deep` (using depth-preferred rules) or if `new_depth >= DEEP_THRESHOLD` (e.g. depth $\ge 2$ or new_depth > recent entry depth).
  - Otherwise stored in `tt_recent` (always replace).
- Capacity is divided evenly ($N / 2$ per tier) so that total memory usage remains constant ($200{,}000$ entries total).

### 6. Baseline Telemetry & Measurement Framework

To evaluate these policies with scientific rigor, the engine and benchmark harness must be instrumented with:
- `tt_probes`: Total TT lookup attempts.
- `tt_hits`: Total successful key matches.
- `tt_usable_hits`: Hits where `entry.depth >= effective_depth` and draw guards permit cutoff consideration.
- `tt_cutoffs`: Cutoffs that immediately terminate `_negamax` (exact or $\alpha \ge \beta$).
- `tt_stores`: Total store operations attempted.
- `tt_same_key_updates`: Stores where key already existed in the table.
- `tt_same_key_overwrites`: Same-key stores that replaced existing entry.
- `tt_same_key_rejected`: Same-key stores rejected due to insufficient depth.
- `tt_clears`: Table flushes triggered by capacity limit.

### 8. Audit Conclusions and Recommendations

1. **Architecture Finding**:
   - The Python `dict`-based TT with 64-bit Polyglot Zobrist keys performs reliably and collision-free within typical search budgets.
   - Overwrite protection in `depth_preferred` and `two_tier` successfully eliminates shallow-overwrites-deep corruption and preserves valuable hash moves on fail-low updates.
2. **Production Default Recommendation**:
   - Retain `always_replace` as the production default for Milestone v0.23. The performance delta at depth 5 is minor (+0.18% nodes, -1.95% to -2.95% runtime) and does not justify disrupting production search characteristics until deeper time-controlled searches with search generation aging are introduced.
   - Expose `depth_preferred` and `two_tier` as selectable policies via `tt_replacement_policy` for experimental and tuning purposes.
