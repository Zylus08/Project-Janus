### 1. Executive Summary

Milestone v0.23 audited the Transposition Table (TT) implementation in Project Janus and evaluated three replacement policies under strict scientific controls:
1. `always_replace` (Current baseline): Eager overwrite on every store; flushes table on capacity overflow.
2. `depth_preferred`: Protects deeper entries against shallower updates (`new_depth >= old.depth`), preserves hash moves on fail-low updates, and backfills missing hash moves.
3. `two_tier`: Dual-table architecture partitioning capacity evenly into a depth-protected tier (`tt_deep`) and a shallow/recency tier (`tt_recent`), strictly maintaining total capacity budget (`<= 200,000` entries).

#### Key Experimental Findings
- **Search Equivalence at Depths 3 & 4**: All three policies produced **identical node counts** (13,439 at depth 3; 26,409 at depth 4), **100% best-move agreement**, and **100% root-score agreement**.
- **Selective Divergence at Depth 5**:
  - `always_replace`: 53,707 nodes, median wall-clock time 10.715s.
  - `depth_preferred`: 53,803 nodes (+96 nodes, +0.18%), median wall-clock time 10.506s (-1.95%).
  - `two_tier`: 53,803 nodes (+96 nodes, +0.18%), median wall-clock time 10.398s (-2.95%).
- **Divergence Origin**: In position `white_up_rook` at depth 5, `depth_preferred` and `two_tier` rejected exactly **9 shallower overwrite attempts**, protecting deep entries from being overwritten by shallower LMR/reduced searches. This caused a slight branch re-exploration (+96 nodes) while preserving the exact same root score (+838 cp) and best move (`e2d4`).
- **Tactical and Endgame Fidelity**: Across all 6 benchmark positions and 208 regression tests, 0 regressions in tactical resolution, forced mate finding, draw detection, or legal PV generation were observed.
- **Production Recommendation**: Retain `always_replace` as the default production policy because the node variance (+0.18%) and timing differences are marginal within Python runtime variance, while keeping `depth_preferred` and `two_tier` as fully verified, selectable engine options.

#### Analysis of `white_up_rook` Node Discrepancy
In `white_up_rook`:
1. During iterative deepening, deeper searches evaluate tactical branches at plies 2–4 with depth 4.
2. In `always_replace`, when a reduced LMR move subsequently visits those same transposition keys at effective depth 1 or 2, it blindly overwrites the depth 4 exact entry with an upper bound.
3. In `depth_preferred` and `two_tier`, the shallower update is rejected (`tt_same_key_rejected = 9`), protecting the depth 4 entry.
4. Preserving the deeper entry provided 4 additional usable hits (`2,563` vs `2,559`), slightly altering the move ordering in a non-PV branch and resulting in a small 96-node search tree divergence. Both policies produced identical PVs and root scores.

### 6. Architectural and Memory Considerations

1. **Memory Budget**:
   - In Python, each `TTEntry` dataclass instance requires approximately 56 bytes, plus the dict hash bucket overhead (~8 bytes).
   - At `tt_max_entries = 200,000`, maximum memory footprint is approximately 18–24 MB.
   - In `two_tier`, the capacity is strictly partitioned into `tt_max_entries // 2` for each table (`tt` and `tt_recent`), ensuring the two tables combined never exceed `tt_max_entries`.
2. **Clear Semantics**:
   - The custom `TranspositionTable(dict)` wrapper ensures that any external call to `engine.tt.clear()` (e.g. from UCI `ucinewgame` or test harnesses) automatically clears both primary and secondary tiers.

---

### 7. Recommendations and Conclusion

1. **Default Policy**: Maintain `always_replace` as the production default. The depth-5 search differences (+0.18% nodes, -1.95% to -2.95% median time) are slight and do not justify deviating from the battle-tested default.
2. **Availability**: Expose `depth_preferred` and `two_tier` as configurable options via `tt_replacement_policy` parameter in `JanusSearch`.
3. **Future Extension**: If aging/search generation counters are introduced in future milestones, `depth_preferred` combined with age-based eviction should be revisited for deeper time-controlled searches.
