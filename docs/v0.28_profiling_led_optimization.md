### 1. Executive Summary

Milestone v0.28 executes a strictly profiling-led optimisation of the production-default Project Janus search engine. Following the v0.27 audit—which established that Static Exchange Evaluation (SEE) ordering and pruning offered no statistically significant playing-strength improvement despite node reductions—production defaults remain strictly configured with SEE ordering **disabled**, SEE pruning **disabled**, Transposition Table policy set to `always_replace`, and check extensions **disabled**.

Rather than introducing speculative chess heuristics, evaluation tweaks, or algorithmic search alterations, this milestone targeted the single largest computational bottleneck in the engine's hot path identified by profiling the production configuration across the canonical benchmark suite.

#### Key Highlights & Results

1. **Hotspot Identification via `cProfile`:**
   - In the production baseline search across all six canonical benchmark positions at depths 4 and 5 (14,151,538 function calls in 11.33s), the evaluation function `evaluate_white` in `src/janus/evaluation.py` was the **#1 bottleneck in engine code**.
   - It accounted for **1.054s exclusive CPU time (9.3%)** and **2.226s cumulative CPU time (19.6%)** across 44,761 invocations.
   - Root cause: Each evaluation dynamically iterated through a piece-value dictionary, invoked `board.pieces_mask(...)` 12 separate times, performed forward bitboard square scans for every piece (including rooks, queens, and zero-value kings), redundantly re-queried bishop masks for bishop-pair checks, and performed dynamic dictionary and coordinate arithmetic in inner Python loops.

2. **Selected Primary Optimisation:**
   - Implemented precomputed static 64-element piece-square tables (`WHITE_PAWN_TABLE`, `BLACK_PAWN_TABLE`, `KNIGHT_TABLE`, `BISHOP_TABLE`), directly accessed native bitboard attributes (`board.pawns`, `board.knights`, `board.bishops`, `board.rooks`, `board.queens`) intersected with `board.occupied_co[color]`, computed flat-valued piece contributions (rooks and queens) via C-level `.bit_count() * VALUE` without square scanning, skipped zero-value kings, and reused bishop counts for bishop-pair bonuses.
   - **Zero Chess Semantics Drift:** Centipawn scores are 100% mathematically identical to the unoptimised reference on every legal chess board.

3. **Performance Improvements (5 Interleaved Repetitions, Depth 4 & 5):**
   - **Microbenchmark:** 50,000 evaluations executed in 0.808s vs 1.351s (**40.2% faster**).
   - **Depth 4 Benchmark:** Suite median runtime fell from 1.824s to 1.642s (**+9.96% speedup**, NPS increased by **+11.06%**).
   - **Depth 5 Benchmark:** Suite median runtime fell from 3.244s to 2.863s (**+11.72% speedup**, NPS increased by **+13.28%**).
   - **Complex Middlegame (`open_game`, 27,480 nodes):** Median runtime fell from 1.904s to 1.622s (**+14.80% speedup** at depth 5).
   - **Profiler Validation:** `evaluate_white` exclusive CPU time fell from 1.054s to 0.657s (**-37.7%**), cumulative CPU time dropped from 2.226s to 1.510s (**-32.2%**), and forward bitboard scans (`scan_forward`) decreased by 575,602 calls (**-35.7%**).

4. **Correctness & Stability Verification:**
   - **Search Tree Invariance:** Exactly 0 paired move, score, or node count mismatches across all 60 benchmark runs (100% exact parity).
   - **Principal Variations:** 100% legal PV moves verified on board.
   - **Unit Tests:** All **244 / 244 unit tests passing** cleanly in 83.3s (reduced from 96.7s baseline).
   - **UCI Protocol:** Full compatibility verified (`uci`, `isready`, `position`, `go depth 4`, `quit`).

   - It iterated over `PIECE_VALUES.items()` 44,761 times (268,566 loop iterations).
   - It invoked `board.pieces_mask(...)` 12 times per call (537,132 times), querying bitboards through generic method dispatch.
   - For rooks and queens—which have zero positional or square-dependent bonuses—it called `scan_forward` for every piece on the board rather than calculating `count * value`.
   - It scanned kings square-by-square even though king material value is 0 and has no positional bonus.
   - It invoked `pieces_mask` again to check for bishop pairs.
   - It computed center distances and rank bonuses via dynamic coordinate lookups inside inner loops.

### 3. Selected Primary Optimisation: Vectorised Bitboard Evaluation

#### Selection Criteria Assessment

1. **Measured Runtime Contribution:** High. `evaluate_white` represents 19.6% cumulative search time and 9.3% exclusive time.
2. **Correctness Risk:** Extremely Low. The mathematical evaluation function is unchanged. Every piece receives the identical material and positional value.
3. **Clear Mechanism:** Eliminates method call overhead, dictionary iteration, square loops on rooks/queens/kings, and precomputes piece-square lookup arrays.
4. **Testability:** Readily verified by asserting exact equality of scores across thousands of arbitrary board positions.
5. **Measurable Outcome:** Reduces evaluation time by ~40%, providing ~10% to ~15% overall search speedup without changing node counts.
6. **Diff Size:** Small, localized entirely within `src/janus/evaluation.py`.

#### Concrete Implementation

In `src/janus/evaluation.py`:

```python
# Precomputed piece-square tables combining base piece values and positional bonuses
WHITE_PAWN_TABLE: tuple[int, ...] = tuple(
    PIECE_VALUES[chess.PAWN] + WHITE_PAWN_RANK_BONUS[sq] for sq in chess.SQUARES
)
BLACK_PAWN_TABLE: tuple[int, ...] = tuple(
    PIECE_VALUES[chess.PAWN] + BLACK_PAWN_RANK_BONUS[sq] for sq in chess.SQUARES
)
KNIGHT_TABLE: tuple[int, ...] = tuple(
    PIECE_VALUES[chess.KNIGHT] + CENTER_BONUS[sq] for sq in chess.SQUARES
)
BISHOP_TABLE: tuple[int, ...] = tuple(
    PIECE_VALUES[chess.BISHOP] + CENTER_BONUS[sq] for sq in chess.SQUARES
)
ROOK_VALUE: int = PIECE_VALUES[chess.ROOK]
QUEEN_VALUE: int = PIECE_VALUES[chess.QUEEN]


def evaluate_white(board: chess.Board) -> int:
    """Evaluate a non-terminal position from White's perspective."""
    score = 0
    occ_w = board.occupied_co[chess.WHITE]
    occ_b = board.occupied_co[chess.BLACK]

    # Pawns
    for square in chess.scan_forward(board.pawns & occ_w):
        score += WHITE_PAWN_TABLE[square]
    for square in chess.scan_forward(board.pawns & occ_b):
        score -= BLACK_PAWN_TABLE[square]

    # Knights
    for square in chess.scan_forward(board.knights & occ_w):
        score += KNIGHT_TABLE[square]
    for square in chess.scan_forward(board.knights & occ_b):
        score -= KNIGHT_TABLE[square]

    # Bishops
    w_bishops = board.bishops & occ_w
    w_bishop_cnt = w_bishops.bit_count()
    for square in chess.scan_forward(w_bishops):
        score += BISHOP_TABLE[square]
    if w_bishop_cnt >= 2:
        score += 25

    b_bishops = board.bishops & occ_b
    b_bishop_cnt = b_bishops.bit_count()
    for square in chess.scan_forward(b_bishops):
        score -= BISHOP_TABLE[square]
    if b_bishop_cnt >= 2:
        score -= 25

    # Rooks (flat value, no square-dependent bonus)
    score += (board.rooks & occ_w).bit_count() * ROOK_VALUE
    score -= (board.rooks & occ_b).bit_count() * ROOK_VALUE

    # Queens (flat value, no square-dependent bonus)
    score += (board.queens & occ_w).bit_count() * QUEEN_VALUE
    score -= (board.queens & occ_b).bit_count() * QUEEN_VALUE

    # Encourage castling rights as a small proxy for king safety / flexibility.
    score += 8 * (
        int(board.has_kingside_castling_rights(chess.WHITE))
        + int(board.has_queenside_castling_rights(chess.WHITE))
        - int(board.has_kingside_castling_rights(chess.BLACK))
        - int(board.has_queenside_castling_rights(chess.BLACK))
    )
    return score
```

### 9. Recommended Next Bottleneck for Future Milestones

Following the successful resolution of the evaluation bottleneck, the profile indicates the next high-confidence targets:

1. **Lazy Check Detection in LMR (`_negamax`):**
   - In `_negamax`, line 805 eagerly invokes `gives_check = board.gives_check(move)` for every move in the search loop, even when `moves_searched < 3`, `depth < 3`, or when the move is already a capture or promotion. Short-circuiting this check directly inside `eligible_for_lmr` will eliminate tens of thousands of `gives_check` calls per search.
2. **Quiescence Legal Move Check Redundancy:**
   - At the leaf of `_negamax` and entry to `_quiescence`, `if not any(board.generate_legal_moves()): return 0` is executed on consecutive plies for the same board, and runs before `stand_pat >= beta` cutoffs in `_quiescence`. Deferring stalemate verification until after stand-pat cutoff and capture generation can eliminate substantial redundant move generation in quiescence search.
