### 1. Executive Summary

Milestone v0.29 executes an autonomous, profiling-directed optimisation of the search hot path in Project Janus: **Lazy Late Move Reduction (LMR) Check Detection**. 

In the v0.28 profiling audit, `chess.Board.gives_check(move)` was identified as an expensive recurring primitive invoked 30,482 times during a 6-position search across depths 4 and 5. Investigation of `src/janus/search.py` revealed that `gives_check = board.gives_check(move)` was executed eagerly at every move in the negamax move loop, even when the move was fundamentally ineligible for LMR due to cheaper preconditions (e.g. first 3 moves, shallow subtree depth < 3, root ply == 0, node in check, tactical captures, pawn promotions, or killer moves).

By deferring the evaluation of `board.gives_check(move)` until all cheaper, necessary eligibility preconditions pass, the engine eliminates **28,652 unnecessary check evaluations (-94.0%)** without altering LMR eligibility, chess semantics, search tree topology, or production configuration defaults.

#### Key Findings & Performance Outcomes

1. **Call Count Reduction:**
   - **Depth 4:** 8,241 eager calls reduced to 51 lazy calls (**8,190 avoided, -99.4%**).
   - **Depth 5:** 22,241 eager calls reduced to 1,779 lazy calls (**20,462 avoided, -92.0%**).
   - **Combined (D4 + D5):** 30,482 calls reduced to 1,830 calls (**28,652 calls avoided, -94.0%**).

2. **Benchmark Speedup (5 Interleaved Repetitions, Depths 4 & 5):**
   - **Depth 4:** Median suite runtime improved from 5.297s to 5.005s (**+5.51% speedup**, NPS up **+5.84%**).
   - **Depth 5:** Median suite runtime improved from 11.143s to 9.586s (**+13.97% speedup**, NPS up **+16.24%**).
   - **Complex Middlegame (`open_game`, 27,480 nodes):** Median runtime fell from 6.392s to 5.477s (**+14.30% speedup** at depth 5).

3. **Search Invariance & Correctness:**
   - **Node Count Invariance:** Exactly 26,409 nodes at Depth 4 and 53,707 nodes at Depth 5 (100% bit-for-bit node equality across all 60 benchmark runs).
   - **Move & Score Invariance:** 0 best move discrepancies, 0 root score discrepancies, 0 PV discrepancies.

### 2. Original Eager-Check-Detection Control Flow & Problem Analysis

In the negamax move loop in `src/janus/search.py` (v0.28):

```python
        for move in moves:
            is_capture = board.is_capture(move)
            is_promotion = move.promotion is not None
            gives_check = board.gives_check(move)  # <--- COMPUTED EAGERLY ON EVERY MOVE

            eligible_for_lmr = (
                self.enable_lmr
                and moves_searched >= 3
                and depth >= 3
                and ply > 0
                and not in_check
                and not is_capture
                and not is_promotion
                and not gives_check
                and (
                    ply >= len(self.killers)
                    or (move != self.killers[ply][0] and move != self.killers[ply][1])
                )
            )
```

#### Why Eager Evaluation Was Inefficient

In `python-chess`, `board.gives_check(move)` is a computationally expensive method. It retrieves the enemy king square, determines if `move.to_square` attacks the king, checks for discovered checks along slider ray lines by clearing `move.from_square`, and validates en-passant/castling check implications.

In eager evaluation, this expensive routine was executed unconditionally for:
1. **The first three moves (`moves_searched < 3`):** In every search node, moves 0, 1, and 2 are never reduced under conservative LMR.
2. **Shallow depths (`depth < 3`):** Nodes at depth 1 and 2 never reduce moves under LMR.
3. **The root node (`ply == 0`):** Root moves are never reduced under LMR.
4. **Nodes in check (`in_check == True`):** Evasions are never reduced under LMR.
5. **Tactical captures (`is_capture == True`):** Captures are never reduced under LMR.
6. **Pawn promotions (`is_promotion == True`):** Promotions are never reduced under LMR.
7. **Killer moves:** Moves matching killer slots 1 or 2 are protected from reduction.

Furthermore, line-by-line inspection of `src/janus/search.py` confirmed that `gives_check` was not referenced anywhere else in `_negamax`. Computing it on every move was purely wasted CPU cycles.

### 3. Precise Code Change & Invariance Proof

In `src/janus/search.py`, the eager assignment was removed and `not board.gives_check(move)` was appended as the final condition of the short-circuit boolean conjunction:

```python
        for move in moves:
            is_capture = board.is_capture(move)
            is_promotion = move.promotion is not None

            eligible_for_lmr = (
                self.enable_lmr
                and moves_searched >= 3
                and depth >= 3
                and ply > 0
                and not in_check
                and not is_capture
                and not is_promotion
                and (
                    ply >= len(self.killers)
                    or (move != self.killers[ply][0] and move != self.killers[ply][1])
                )
                and not board.gives_check(move)
            )
```

#### Invariance Proof

Under Python's short-circuit evaluation semantics:
- `is_capture` and `is_promotion` are preserved at loop top because they are subsequently referenced on line 907 for killer/history heuristics (`if not is_capture and not is_promotion:`).
- For any move where any of `self.enable_lmr`, `moves_searched >= 3`, `depth >= 3`, `ply > 0`, `not in_check`, `not is_capture`, `not is_promotion`, or killer exclusions evaluates to `False`:
  - Python immediately short-circuits.
  - `board.gives_check(move)` is never called.
  - `eligible_for_lmr` evaluates to `False`, identical to the eager logic.
- For any move where all 8 prior preconditions are `True`:
  - `not board.gives_check(move)` is evaluated.
  - If the move delivers check, `eligible_for_lmr` is `False`. The checking move is strictly protected from reduction.
  - If the move does not deliver check, `eligible_for_lmr` is `True`. The quiet move is reduced.
- Therefore, the boolean value of `eligible_for_lmr` is **mathematically identical for every single move in every search node**.

At depth 4, the search tree reaches `depth >= 3` only at ply 1. Consequently, very few non-capture moves searched 4th or later ever meet the depth threshold.
