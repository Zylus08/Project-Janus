# Project Janus v0.34.2 — Match Harness Reliability & Supervised Engine Lifecycle

## Executive Summary

During the v0.34 playing-strength evaluation, an unhandled infrastructure defect silently invalidated Games 56 through 100 of the primary 100-game match. A single long-lived `chess.engine.SimpleEngine` process died mid-game; the harness caught the resulting `EngineTerminatedError: engine event loop dead` inside the move search loop, misclassified it as an immediate chess forfeit by whichever engine was to move on ply 1, and continued through Game 100. This created 44 synthetic zero-second games with an artificial 39% White / 66% Black score distortion.

Milestone **v0.34.2** repairs the engine lifecycle and failure-handling infrastructure from first principles:
1. **Isolated Supervised Process per Game:** Replaced long-lived engine sessions with `SupervisedEngineSession`, which spawns, initializes, configures, supervises, and deterministically closes fresh subprocesses for every single game.
2. **Explicit Failure Policy:** Infrastructure failures (process crashes, initialization timeouts, move budget overruns, broken pipes, illegal moves) are strictly separated from chess terminations and are **never** counted as chess wins, losses, or draws.
3. **Audit Trail of Attempts:** Every attempt is preserved in `attempts.json`. Failed attempts can be retried with identical opening FEN and color assignments up to a strict bound (max 2 retries per slot).
4. **Paired Integrity:** Pairs are admitted into paired statistical analysis if and only if both colour-reversed games complete validly.
5. **Deterministic Exit Codes:** The harness exits with a nonzero exit code if the planned valid games or complete pairs target is not achieved.
6. **Regression Suite:** Added 15 failure-injection and lifecycle tests verifying all failure modes.

## 1. Root Cause Analysis of v0.34 Failure

### 1.1 The Long-Lived Process Defect
In `scripts/match_v034.py`, engines were initialized once before the 100-game loop using `python-chess`'s `SimpleEngine.popen_uci()`:

```python
with (
    chess.engine.SimpleEngine.popen_uci(base_cmd, cwd=base_dir, env=env_base) as base_eng,
    chess.engine.SimpleEngine.popen_uci(cand_cmd, cwd=cand_dir) as cand_eng,
):
    for i in range(start_index, games):
        ...
        play_one_game(base_eng, cand_eng, ...)
```

Under this pattern:
- The engines shared a single process and an internal `asyncio` event loop managed by `python-chess`.
- At Game 56 (Move 99), `Janus-v0.34` terminated with exit code 1.
- At Game 58 (Move 6), `Janus-v0.30` also terminated.
- Once an engine process died, `SimpleEngine`'s event loop closed. Any subsequent `engine.play()` call immediately raised `EngineTerminatedError: engine event loop dead`.

### 1.2 The Misclassification of Infrastructure Errors as Chess Forfeits
In `scripts/match_v034.py`, the move search loop contained:

```python
try:
    res = current_engine.play(board, limit, info=chess.engine.INFO_ALL)
    ...
except Exception as exc:
    result_string = "0-1" if board.turn == chess.WHITE else "1-0"
    termination_reason = f"engine crash ({curr_name}): {exc}"
    break
```

When `EngineTerminatedError` was caught on Ply 1 (where `board.turn == chess.WHITE`), the harness assigned `result_string = "0-1"`. It then mapped this into:
```python
if result_string == "0-1":
    cand_score = 0.0 if cand_color == chess.WHITE else 1.0
```
Because White always moves first on ply 1:
- When Candidate was White (even games), it was assigned a Loss (0.0).
- When Candidate was Black (odd games), White "forfeited", giving Candidate a Win (1.0).

This explains the artificial disparity where Candidate scored 39.1% as White and 66.0% as Black in the aggregate report.

## 2. Architecture of the Repaired Harness

### 2.1 SupervisedEngineSession (`src/janus/engine_session.py`)
To isolate each game and guarantee deterministic teardown on Windows, we implemented `SupervisedEngineSession`:

- **Subprocess Isolation:** Each engine instance runs in its own subprocess with independent pipes (`stdin`, `stdout`, `stderr`).
- **Non-blocking Pipe Readers:** Standard Windows pipe operations can deadlock if a child process hangs without flushing. `SupervisedEngineSession` uses background daemon reader threads pumping lines into thread-safe queues.
- **Strict Startup Handshake:** Sends `uci`, requires `uciok` within a bounded `startup_timeout` (default 5.0s), applies options via `setoption`, and requires `readyok` in response to `isready`.
- **Search Supervision:** Sends `go movetime <ms>`, monitors `info` telemetry (depth, score, nodes), enforces a hard time budget (`movetime_ms + move_timeout_padding`), and verifies that the returned `bestmove` is legal from the current board position.
- **Deterministic Teardown:**
  1. Sends `quit`.
  2. Waits up to 1.5s for graceful exit.
  3. Escalates to `terminate()` (1.0s timeout).
  4. Forcefully executes `kill()` if unresponsive.
  5. Explicitly closes `stdin`, `stdout`, and `stderr` streams to prevent resource leaks.

### 2.2 Failure Categories
The session classifies failures into distinct exception types inheriting from `EngineError`:
- `EngineInitializationError`: Failure to spawn subprocess or execute binary.
- `EngineTimeoutError`: Engine failed to return `uciok`, `readyok`, or `bestmove` within budget.
- `EngineProcessError`: Engine crashed with a nonzero exit code or broke its communications pipe.
- `EngineProtocolError`: Engine sent malformed UCI tokens, null moves, or illegal moves.

### 2.3 Failure Policy and Match Integrity (`scripts/match_v0342.py`)
1. **Game Validity:** A game is valid (`status = "valid_chess"`) if and only if both engines operate without error and the game reaches a standard chess termination (checkmate, stalemate, insufficient material, repetition, 50-move rule, or ply limit).
2. **Infrastructure Failure Isolation:** Any `EngineError` sets `status = "infrastructure_failure"`. The failure is logged with `failed_engine`, `failure_category`, `error_message`, `exit_code`, and `stderr_snippet`.
3. **Zero Rating Impact:** Infrastructure failures are excluded from wins, draws, losses, score percentage, and Elo calculations.
4. **Bounded Retries with Invariance:** If an attempt fails due to an infrastructure error:
   - Up to 2 retries are permitted for that game slot.
   - The opening position (`start_fen`) and candidate colour assignment (`candidate_color`) remain identical.
   - A fresh engine process pair is spawned for the retry.
5. **Audit Retention:** All attempts (successful and failed) are recorded in `attempts.json`.
6. **Pair Filtering:** If either game in an opening pair fails and cannot be recovered, the entire pair is marked `incomplete` and excluded from paired statistics (sign test, paired t-test, paired bootstrap).
7. **Match Abort Threshold:** If cumulative infrastructure failures reach 5 across the match, the harness aborts immediately to prevent infinite retry loops.
8. **Exit Codes:** If target valid games or target complete pairs are unmet, `scripts/match_v0342.py` exits with code 1.
