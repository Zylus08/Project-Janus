**Author:** Senior Chess Engine Architect, Time-Control Systems Engineer  
**Status:** Approved Architecture Specification

## 1. Executive Summary

Project Janus v0.34 established a calibrated tapered evaluation system with validated positional strength under fixed-movetime search conditions (e.g., 500 ms/move). However, real-world chess play, automated rating lists (CCRL, CEGT, SPCC), and competitive engine matches operate primarily under clock-based time controls, notably Fischer increment time controls (e.g., 10m + 0.1s, 3m + 2s, or blitz 5m + 5s).

Prior to v0.35, the Janus UCI interface and search subsystem lacked any clock-based time allocation logic:
- `wtime`, `btime`, `winc`, `binc`, and `movestogo` parameters sent with UCI `go` were ignored, falling back to a fixed depth of 5 with no time limit.
- Only explicit `movetime` was parsed into a deadline limit.
- Deadline checks in the search loop operated solely inside `_negamax` and `_quiescence` at 256-node intervals, without checking the remaining budget at iterative-deepening depth boundaries.

This design specification defines the architecture, mathematical model, boundary conditions, protocol semantics, and testing framework for an adaptive, clock-aware time manager in Project Janus v0.35.

## 2. Reconnaissance of Existing Implementation

### 2.1 UCI Command Parsing (`src/janus/uci.py`)
In `src/janus/uci.py` (lines 207–223):
```python
elif command == "go":
    depth = 5
    time_limit = None
    if "depth" in parts:
        try:
            depth = max(1, int(parts[parts.index("depth") + 1]))
        except (ValueError, IndexError):
            depth = 5
    if "movetime" in parts:
        try:
            time_limit = max(1, int(parts[parts.index("movetime") + 1])) / 1000.0
            depth = 64
        except (ValueError, IndexError):
            time_limit = 1.0
            depth = 64
    start_search(board, depth, time_limit)
```
**Defects and Missing Behavior:**
1. Clock tokens (`wtime`, `btime`, `winc`, `binc`, `movestogo`) are unrecognized. If received without `movetime` or `depth`, the engine executes an unconstrained search to depth 5, potentially consuming multiple seconds in complex middle-game positions.
2. In a clock match where a side has 100 ms left, the engine does not know it is in time trouble and will forfeit on time.
3. Asymmetric increments or asymmetric clocks between White and Black cannot be processed.

### 2.2 Search Loop and Limits (`src/janus/search.py`)
In `src/janus/search.py`:
- `self.deadline = None if time_limit is None else start + max(0.001, time_limit)`
- Monotonic clock is used (`time.monotonic()`), which prevents wall-clock adjustments from corrupting search deadlines.
- Node check frequency:
  ```python
  def _check_stop(self) -> None:
      if self.stop_event is not None and self.stop_event.is_set():
          raise SearchTimeout
      if self.deadline is not None and (self.nodes & 255) == 0:
          if time.monotonic() >= self.deadline:
              raise SearchTimeout
  ```
- Boundary check: The iterative-deepening loop in `search()` does not check `self.deadline` between iterations. If an iteration finishes with 1 ms remaining, depth $d+1$ is initiated, which will search up to 255 nodes before noticing the timeout.

### 2.3 Supervised Engine Lifecycle (`src/janus/engine_session.py`)
`SupervisedEngineSession` provides robust subprocess management, pipes, non-blocking readers, and graceful shutdown.
`play_move` currently hardcodes:
```python
self._send_line(f"go movetime {movetime_ms}")
```
To support clock-based and Fischer increment qualification and strength matches, `engine_session.py` needs to support passing clock parameters (`wtime`, `btime`, `winc`, `binc`, `movestogo`).

## 3. Supported Time-Control Semantics

The v0.35 time management subsystem explicitly separates and handles three operational modes:

### Mode A: Fixed Movetime (`go movetime X`)
- Example: `go movetime 500`
- Units: Milliseconds (integer).
- Allocation: Exactly $X / 1000.0$ seconds.
- Semantics: Bypasses clock calculation entirely. No safety margin or move-counter estimation is applied. Existing fixed-movetime behavior is preserved identically for backward compatibility and reproducible benchmarking.

### Mode B: Classical Clock Control Without Increment (`go wtime X btime Y [movestogo N]`)
- Example: `go wtime 60000 btime 60000`
- Units: Milliseconds (integers).
- Side-to-move detection: Active board color (`board.turn`) determines whether `wtime` or `btime` is the subject clock.
- Allocation: Budget is partitioned across estimated moves remaining, buffered by a safety reserve.

### Mode C: Fischer Increment Control (`go wtime X btime Y winc A binc B [movestogo N]`)
- Example: `go wtime 600000 btime 600000 winc 100 binc 100`
- Units: Milliseconds (integers).
- Semantics: Increment for the active side is weighted and added to the move budget, ensuring the engine utilizes its increment effectively without overspending its base reserve.

### Edge Conditions and Malformed Inputs
- **Low clock ($\le$ safety reserve):** Engine enters emergency time mode, allocating an ultra-low budget (e.g. 5–10 ms) to emit a legal move without flagging.
- **Near-zero or negative clock:** Clamped to a minimal legal threshold (e.g. 1–5 ms) rather than throwing an exception or hanging indefinitely.
- **Asymmetric controls:** Different clock values or increments for White and Black must be attributed strictly to the side to move (`board.turn`).
- **Malformed inputs:** Missing arguments, negative values, non-numeric strings, or mixed options must be sanitized without raising unhandled exceptions.

## 4. Mathematical Model for Adaptive Allocation

### 4.1 Base Formulation
Let:
- $T_{\text{rem}}$ = Remaining clock for side to move (ms)
- $I$ = Increment for side to move (ms, defaults to 0)
- $R_{\text{safe}}$ = Safety reserve for transmission, protocol, and OS jitter (default: 50 ms)
- $N_{\text{mtg}}$ = Moves to go until next time control (if specified by `movestogo`), or $N_{\text{est}}$ (estimated default: 30 moves)
- $W_{\text{inc}}$ = Increment utilization weight (default: 0.85)
- $B_{\text{min}}$ = Minimum search budget (default: 10 ms)
- $P_{\text{max}}$ = Maximum fraction of remaining clock allowed on any single move (default: 0.20 or 20%)

### 4.2 Allocation Pipeline
1. **Usable Base Time:**
   $$T_{\text{usable}} = \max\left(0, T_{\text{rem}} - R_{\text{safe}}\right)$$

2. **Base Move Allocation:**
   $$A_{\text{base}} = \frac{T_{\text{usable}}}{N_{\text{mtg}}}$$

3. **Increment Addition:**
   $$A_{\text{target}} = A_{\text{base}} + W_{\text{inc}} \times I$$

4. **Safety Clamping:**
   - Maximum budget cap:
     $$B_{\text{max}} = \max\left(B_{\text{min}}, \min\left(T_{\text{rem}} - R_{\text{safe}}, T_{\text{rem}} \times P_{\text{max}} + I\right)\right)$$
   - Clamped target:
     $$A_{\text{final}} = \text{clamp}\left(A_{\text{target}}, B_{\text{min}}, B_{\text{max}}\right)$$

5. **Emergency Fallback (When $T_{\text{rem}} \le R_{\text{safe}}$):**
   If remaining clock is critically low, $A_{\text{final}} = \max(1, \min(T_{\text{rem}} // 2, B_{\text{min}}))$, ensuring search triggers an immediate depth 1 or fallback move before the flag falls.

6. **Unit Conversion:**
   $$\text{time\_limit (seconds)} = \frac{A_{\text{final}}}{1000.0}$$

## 5. Architectural Component Design

### 5.1 Independent Module: `src/janus/time_manager.py`
A decoupled, stateless or cleanly configurable `TimeManager` class:
- `TimeManagerConfig`:
  - `safety_reserve_ms: int = 50`
  - `default_moves_to_go: int = 30`
  - `increment_weight: float = 0.85`
  - `min_allocation_ms: int = 10`
  - `max_allocation_ratio: float = 0.20`
- Pure function `allocate_time(side_to_move: chess.Color, wtime: Optional[int], btime: Optional[int], winc: Optional[int], binc: Optional[int], movestogo: Optional[int], movetime: Optional[int]) -> float` (returns seconds).
- Completely deterministic, zero side-effects, unit-testable in isolation.

### 5.2 UCI Loop Integration (`src/janus/uci.py`)
- Parse tokens in `go`:
  - `movetime <ms>`
  - `wtime <ms>`
  - `btime <ms>`
  - `winc <ms>`
  - `binc <ms>`
  - `movestogo <int>`
  - `depth <int>`
- If `movetime` is present: direct allocation $ms / 1000.0$, `depth = 64`.
- If `wtime` / `btime` are present: route to `TimeManager.allocate_time(...)`, set `depth = 64`.
- If only `depth` is present: `depth = depth`, `time_limit = None`.
- If `go` with no arguments: default to `depth = 5, time_limit = None` (preserving existing behavior).

### 5.3 Search Loop Boundary Checks (`src/janus/search.py`)
- In `JanusSearch.search()`:
  - Add explicit deadline check at the start of each iterative-deepening iteration:
    ```python
    if self.deadline is not None and time.monotonic() >= self.deadline:
        break
    ```
  - Ensure `best_move` and `best_pv` from the previous completed depth remain intact.

## 6. Risks and Mitigations

| Risk | Cause | Mitigation |
| :--- | :--- | :--- |
| **Clock Overrun / Flagging** | Windows thread scheduling latency or long negamax nodes. | Safety reserve ($R_{\text{safe}} = 50\text{ ms}$) buffers OS jitter; check deadline between iterations and every 256 nodes. |
| **Null/Illegal Move on Timeout** | Interruption before depth 1 completes. | Search initializes `best_move = legal_moves[0]` fallback; UCI verifies move legality before emission. |
| **Increment Overspending** | Large increment causing excessive base depletion. | Increment addition is bounded by remaining clock and clamped to $B_{\text{max}}$. |
| **State Leakage Across Moves** | Stateful time manager retaining stale clock values. | `allocate_time` is purely functional with respect to UCI inputs and board turn. |
| **Regression in Fixed Movetime** | Time manager modifying `movetime` logic. | `movetime` branch explicitly bypasses clock allocation logic. |

## 7. Qualification and Benchmarking Protocol

1. **Unit Tests (`tests/test_time_manager.py`):** 16 explicit test cases verifying all semantics, boundary conditions, edge cases, deterministic calculations, and zero state leakage.
2. **Benchmark Harness (`scripts/benchmark_time_management_v035.py`):** Measure actual duration vs allocated budget across fixed movetime, clock-only, and Fischer increment modes; record latency distribution and deadline overshoot.
3. **Smoke Match Qualification (`analysis/v0.35/qualification/`):** Short supervised matches verifying process lifecycles, clock decrements, increment handling, and protocol compliance.
4. **Controlled Strength Experiment (`analysis/v0.35/strength_match/`):** Paired Fischer increment match comparing Janus v0.34 with adaptive time management vs reference baseline under identical conditions.
