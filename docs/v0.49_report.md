## 1. Executive Summary & Provenance

Project Janus v0.49 investigated whether moving move-selection operations into compiled native code can eliminate Python move-ordering overhead without introducing search-semantic drift, and whether history scoring and killer move prioritization can be optimized within the lazy search framework.

Across an exhaustive series of microbenchmarks, fixed-depth search evaluations, and 7-tier fixed-time ladders:

1. **Native C Move Picker (Candidate N1):**
   - Implemented a native C kernel (`analysis/v0.49/native/move_picker.c`) compiled with MSVC 2022 (`cl.exe /O2 /LD`).
   - Achieved **exact 100.0% node-for-node and score-for-score equivalence to K0 (405,197 nodes at Depth 4)** across all 37 diagnostic positions.
   - Reduced pure move-sorting execution time by **$-52.2\%$** (from 1.562s to 0.746s).
   - **The Micro-Kernel Paradox:** Despite the $2\times$ faster sorting in C, end-to-end wall-clock search runtime regressed by **$+6.66\%$** (20.63s vs 19.35s). Pre-evaluating move scores into Python lists and marshaling arrays across the `ctypes` boundary incurred more interpreter overhead than the C DLL saved.
2. **History Optimization (Candidate H2):**
   - Stage-separating the move-ordering pipeline into Tactical First $\to$ Quiets Deferred eliminated **670,392 history table lookups** at Depth 4 (a **$-69.6\%$ reduction**), while maintaining 97.3% move agreement with K0 and zero blunders.
3. **Killer Move Integration (Candidate K1):**
   - Prioritizing 2-slot killers before quiets evaluated 37,985 killer opportunities, but list partitioning overhead in Python increased search runtime by $+4.31\%$.
4. **Fixed-Time Decision Quality:**
   - Evaluated across 7 budget tiers (50ms to 3000ms), Candidate L1 maintained 100.0% move agreement with K0 at short time controls and matched Stockfish 19 reference moves at identical rates across all tiers (e.g. 27.0% vs 27.0% at 180ms; 32.4% vs 32.4% at 500ms). Candidate N1 matched K0 in 97.3% of positions at 180ms.
5. **Disposition:** **Category B (Efficiency Improvement Retained, Strength Unconfirmed)**. Baseline K0 remains the immutable production default.

## 3. Native Move-Picker Feasibility & Implementation (Phases B & C)

The feasibility investigation identified that offloading narrow sorting routines to a native C DLL via `ctypes` faces a severe boundary cost:
- Allocating `(ctypes.c_int * n)` in Python and passing pointers across the C boundary requires $\sim 2.5\text{--}3.0\ \mu\text{s}$ per call.
- For typical chess positions ($N \approx 25\text{--}40$ moves), CPython's internal `list.sort()` (Timsort) already executes in $3.4\text{--}5.2\ \mu\text{s}$.
- Microbenchmarks confirmed that native batch sorting only begins to outperform `list.sort()` when $N \ge 50$. Repeated per-move calls (`native_select_next_best`) cost $8.1\text{--}13.8\ \mu\text{s}$, confirming that per-move native calls in Python are unviable.

## 5. Native Performance Evaluation (Phase E)

At Depth 4 on the 37-position diagnostic corpus:
- **Baseline K0:** 19.35 s (Ordering time: 1.562 s)
- **Candidate N1:** 20.63 s (Ordering time: 0.746 s, **$-52.2\%$**)
- **Net Search Delta:** **$+6.66\%$ runtime regression**.
- **Explanation:** In K0, `moves.sort(key=...)` evaluates move keys on demand inside CPython's C sort loop. In N1, Python must evaluate `scores = [self._move_order_score(...) for m in moves]` in advance and marshal arrays into `ctypes`, incurring more interpreter overhead than the C DLL saves.
