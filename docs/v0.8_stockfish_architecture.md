## 2. Deep Subsystem Dissection

### 1. Search Subsystem (`src/search.cpp`)

Stockfish's search architecture is built on **Principal Variation Search (PVS)** inside an **iterative deepening** framework, utilizing **aspiration windows** and aggressive, mathematically tuned pruning.

```
Iterative Deepening (depth = 1, 2, 3...)
  └── Aspiration Window [alpha = prev_score - delta, beta = prev_score + delta]
        └── search<PVNode> / search<NonPVNode>
              ├── Transposition Table Probe & Cutoff
              ├── Null Move Pruning (NMP)
              ├── ProbCut & Futility Pruning
              ├── MovePicker (Staged: TT -> Captures -> Killers -> History -> Quiets)
              ├── Late Move Reductions (LMR)
              └── qsearch (Captures, promotions, check evasions)
```

#### Key Architectural Components
1. **Principal Variation Search (PVS / Alpha-Beta with Zero-Window Search):**
   - The first move (usually the TT move) is searched with a full $[\alpha, \beta]$ window.
   - All subsequent candidate moves are searched with a "zero-window" (null window) $[\alpha, \alpha + 1]$. If a move raises alpha, it is re-searched with the full window. This exploits the invariant that most moves fail low.
2. **Aspiration Windows:**
   - Instead of starting each iteration with $[-\infty, +\infty]$, Stockfish sets a narrow window around the previous iteration's score: $[\text{score} - \delta, \text{score} + \delta]$ (typically $\delta \approx 10\text{--}25\text{ cp}$). If search fails low or high, the window is widened exponentially. This yields a 15–20% node reduction at deeper depths.
3. **Null Move Pruning (NMP):**
   - If the side to move has an overwhelming advantage, it passes its turn ("null move") and conducts a reduced-depth search ($R \approx 3\text{--}4$). If the opponent still cannot make threats, the node cuts off immediately without searching legal moves.
4. **Late Move Reductions (LMR):**
   - Moves ordered late in the list (after TT move, captures, and killers) are searched at reduced depth ($\text{depth} - R$) based on a logarithmically scaled lookup table (`lmrDivisor`). If a reduced move shows promise, it is re-searched at full depth.

### 2. Move Ordering & History Subsystem (`src/movepick.cpp`, `src/history.h`)

Alpha-beta pruning efficiency is determined almost entirely by move ordering: searching the best move first achieves $O(b^{d/2})$ complexity instead of $O(b^d)$.

#### Stockfish's Staged Move Picker (`Stages` in `src/movepick.cpp`):
1. **`MAIN_TT`:** Probe the transposition table. If a best move exists, test it first. If it produces a $\beta$-cutoff, **zero further moves are generated**.
2. **`CAPTURE_INIT` / `GOOD_CAPTURE`:** Generate captures and promotions. Score using Static Exchange Evaluation (SEE):
   - Winning/equal captures ($\text{SEE} \ge 0$) ordered by MVV/LVA.
3. **`QUIET_INIT` / `GOOD_QUIET`:** Generate quiet moves. Order via:
   - **Killer Moves:** Up to 2 quiet moves per ply that caused a $\beta$-cutoff in sibling subtrees.
   - **Countermoves:** Moves that previously refuted the opponent's previous move.
   - **History Heuristic:** Tables indexed by `[color][piece][to_square]` tracking successful $\beta$-cutoffs.
4. **`BAD_CAPTURE`:** Losing captures ($\text{SEE} < 0$) searched last.

*Relevance to Janus:*  
Janus currently calls `list(board.legal_moves)` and sorts ALL moves using only static MVV/LVA. Introducing **Killer Moves** and **History Heuristic** requires zero board redesign and directly transfers to Python.

### 3. Quiescence Search Subsystem (`src/search.cpp:qsearch`)

Quiescence search resolves tactical instability (checks, trades, promotions) before applying static evaluation.

#### Stockfish vs Janus Quiescence Comparison

| Feature | Stockfish 19 (`qsearch`) | Project Janus (`_quiescence`) | Architectural Significance |
| :--- | :--- | :--- | :--- |
| **TT Probing in QSearch** | Full TT probe with cutoff & best move | None (TT disabled in QSearch) | High (avoids re-evaluating identical tactical trades) |
| **Move Generation** | Staged captures via `MovePicker` | `generate_legal_captures()` + 8th-rank promotions | Similar efficiency; Janus now skips quiet moves |
| **Stand-Pat Cutoff** | `if (standPat >= beta) return beta;` | `if stand_pat >= beta: return beta` | Identical alpha-beta stand-pat semantics |
| **Delta Pruning (Futility)** | Prunes captures where `standPat + piece_val + 200 < alpha` | None (all captures searched) | **Major Opportunity:** Eliminates searching losing captures |
| **Check Evasions** | Generates legal evasions if in check | Generates all legal moves if in check | Identical correctness invariant |

### 4. Evaluation & NNUE Subsystem (`src/evaluate.cpp`)

Stockfish 19 relies on **NNUE (Efficiently Updatable Neural Network)** with the `SFNNv16` architecture:
- **Feature Space:** HalfKP (King-Piece combinations: king square $\times$ piece type $\times$ piece square).
- **Inference Efficiency:** The first layer is an **accumulator** updated incrementally during `board.push()` and `board.pop()` using vector instructions (AVX-512/AVX2). Only the small output MLP is evaluated at leaf nodes.
- **Role in Search:** Static evaluation is called strictly on non-checking leaves.

*Relevance to Janus:*  
Training and running an NNUE network in pure Python would be computationally disastrous (Python matrix multiplication without C/SIMD bindings is orders of magnitude too slow). However, Janus's handcrafted evaluation can adopt Stockfish's **classical piece-square and king safety terms** (e.g. open file penalties near the king).

### 5. Position Representation & Move Generation (`src/position.h`)

- **Stockfish:** Custom 64-bit bitboards with staged move generation (`MovePicker`), in-place board state modification (`do_move` / `undo_move`), and Zobrist keys updated incrementally via XOR.
- **Janus:** Relies on `python-chess`'s native C/Python bitboards and `board.push()` / `board.pop()`.
- **Key Performance Takeaway:** In Python, avoiding wrapper object allocations (as demonstrated in our v0.6 bitmask scan optimization) is the primary driver of performance.

### 6. Transposition Table Subsystem (`src/tt.h`)

Stockfish's transposition table is engineered for CPU cache locality:
- **Cluster Layout:** The hash table is divided into clusters of 3 entries (each cluster is exactly 32 bytes, fitting within standard 64-byte L1 CPU cache lines).
- **Replacement Policy:** An entry replaces another in its cluster if:
  1. The new entry has a deeper search depth, OR
  2. The existing entry has an older generation (aging counter incremented every search).
- **Key Representation:** 64-bit integer Zobrist hash with 16-bit key verification.

*Relevance to Janus:*  
Janus currently uses `board.fen(en_passant="legal")` string keys in a Python `dict`. While safe and collision-free, string hashing allocates strings and is slower than Python integer tuple hashing (`board._transposition_key()`).
